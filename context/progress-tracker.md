Fixed by adding a non-superuser `vidyut_app` role (`docker/postgres-init/01-app-role.sql`, `02-create-databases.sql`) that owns both databases and is used for all migrations/app/test connections — this mirrors how a real RDS master user behaves (not a true superuser, does respect `FORCE RLS`) and is what makes the isolation tests meaningful rather than a false green.

## Architecture Decisions (log as made)

- Server-based on **AWS** (ECS/Fargate + ALB + RDS + ElastiCache + S3 + SES, ap-south-1); modular monolith.
- Multi-tenant shared-schema + Postgres RLS via `withTenant()`; **multi-branch (school groups) in v1**.
- Express (Node server) API · Next.js web (2 apps) · one role-based RN/Expo app · Redis + BullMQ persistent worker.
- **CBSE first**; plans/pricing per market research as-is; **Razorpay** + **FCM** (SMS/WhatsApp provider TBD); AI-agents build / founder reviews.
- Full decision + setup tracker: `prerequisites.md`.
- Build complete CORE before selling; on-demand modules after.
- Single role-based mobile app; dual delivery (shared themed + dedicated branded), plan-gated.
- Prisma schema/client/`withTenant()` live in `packages/db` (not `apps/api`), since Unit 02 predates the Express skeleton (Unit 04); `apps/api` will depend on `@vidyut/db` rather than duplicating it.
- Local Postgres runs as a non-superuser app role (`vidyut_app`), not the Docker image's bootstrap `POSTGRES_USER` — the bootstrap user is a true superuser and bypasses RLS/FORCE RLS unconditionally, which would make local RLS tests a false green. This mirrors real RDS master-user behavior.
- `apps/api` was started in Unit 03, not Unit 04, because Unit 03's own spec requires real, testable HTTP endpoints. It deliberately stops at `createApp()` — no `.listen()`, no rate-limit/OpenAPI/X-Request-Id — leaving those to Unit 04.
- The pipeline-wide rate limiter runs before auth (per `api-conventions.md`'s stated order), so it's necessarily IP-keyed, not per-tenant — a per-tenant limiter would need to run after tenant-context and hasn't been added; revisit if abuse patterns need it.
- OpenAPI is generated directly from the same Zod schemas used for request validation (`@asteasolutions/zod-to-openapi`), not hand-written separately — one source of truth, can't drift.
- `packages/api-client`'s generated `openapi.json`/`schema.ts` are committed, not gitignored, so a fresh clone typechecks immediately without a codegen step.
- Permissions are checked live from the DB on every `requirePermission()` call, never cached into the JWT — an owner's role-permission edit takes effect immediately rather than waiting out the access token's lifetime.
- Refresh tokens are hashed with SHA-256, not argon2 — argon2 is for low-entropy secrets (passwords); a refresh token is already a high-entropy random JWT, so a fast hash is the correct, standard choice and avoids unnecessary latency on every refresh.
- `RolePermission`, `UserRole`, and `BranchMembership` all carry a denormalized `tenantId` beyond `data-model.md` §3's shorthand, so RLS can be enforced directly on each row rather than only transitively through a `Role`/`User` join — required by §1's own "every tenant-owned table carries tenantId" convention.
- Added a `RefreshToken` model beyond the §3 sketch — an unambiguous, direct implication of `api-conventions.md`'s already-explicit "refresh token stored hashed, revocable" requirement, not a new invented feature.
- `/auth/otp/request` and `/auth/login` require a `tenantSlug` field not shown in `api-conventions.md`'s shorthand — phone/email are only unique per tenant, not globally, and `User` is RLS-scoped, so tenant must be resolved before the user lookup. A future hostname/school-code resolution layer can populate this field instead of the client.
- Platform tables (`Plan`/`Subscription`/`ModuleToggle`/`SmsWallet`/`AppBuild`) carry no RLS, per `data-model.md` §13's own "NOT tenant-scoped" label — they're config the platform manages and internal guards read, not a tenant-facing CRUD resource. `AuditLog` (§12) is the exception and stays fully RLS'd like every other domain table.
- Super-admin identity is a separate `PlatformUser` table with its own JWT secret/type/guard, never a nullable `tenantId` on `User` — keeps "every tenant-owned table has a real tenantId" a structural fact, not a convention someone can violate by mistake.
- `packages/db` now owns cross-cutting seeding logic (`seedDefaultRoles`, `seedModuleToggles`), not just `apps/db/prisma/seed.ts` — both the demo seed and real tenant provisioning call the same functions, so they can't silently drift apart the way two independent implementations would.
- Adopted `@tanstack/react-query` in `apps/web-app` starting with the super-admin screens (Unit 05's first client-side data fetching) — already the stated convention in `code-standards.md`, and confirmed necessary in practice: the newer `react-hooks/set-state-in-effect` ESLint rule fails plain `useEffect`+`setState` data-fetching outright.
